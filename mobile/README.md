# Mossvale mobile

Push notifications require a new binary with `expo-notifications` and the matching game/server release. **Settings → Notifications** offers separate opt-ins for world events, invitations and daily return reminders starting after 24 hours away; after first entering the world, a dismissible native prompt offers events and invitations, with daily reminders optional. The OS permission request only follows an explicit Enable action. Token and revocation credentials stay in native SecureStore. Logout removes the local binding immediately and retains a capability-based revoke request for the next connection, without saving an old access token. New accounts start with notifications off; this device remembers each account’s explicit choices and opt-outs. Tapping a notification resumes Mossvale; it never accepts an invite or follows a URL from notification content. Live game notifications are suppressed while the app is in the foreground. New Android `mossvale` channels use `AndroidImportance.HIGH`, default sound and vibration for heads-up alerts. Android's existing channel settings, player overrides and Do Not Disturb remain in control; the app never deletes or recreates the channel to bypass them. See [Android's channel importance guidance](https://developer.android.com/develop/ui/compose/notifications/channels#set-importance).

Before a push-capable build, follow [Expo's push setup](https://docs.expo.dev/push-notifications/push-notifications-setup/): configure FCM v1 credentials in EAS and supply the Firebase Android `google-services.json` as the EAS **file** environment variable `GOOGLE_SERVICES_JSON` (read by `app.config.ts`); use the Firebase application matching `world.mossvale.game`. Configure an APNs key in EAS, enable Push Notifications for the existing Apple App ID, and regenerate its provisioning profile. Keep `EXPO_NO_CAPABILITY_SYNC=1` to preserve existing Apple sign-in capabilities; it means enabling the new Apple capability is a manual prerequisite. No credentials are committed. Enable `MOBILE_PUSH_ENABLED=1` on the game server only after credentials, the native binary, and device delivery are ready. Validate permission accept/deny, every category, foreground suppression, tap-to-resume, token rotation, sign-out while offline and account switching on installed Android and iOS builds. Expo Go and a web deployment alone do not supply this native capability.

Expo SDK 57 app for Android and iOS. It runs the existing online Three.js game in a landscape WebView with the game's touch controls, safe area padding, loading/reconnect screens and screen sleep prevention. Game/server updates still deploy through Mossvale's web release process.

Players can open **Settings → Updates** to see how releases work. Game fixes and content load automatically from the realm; wallet sign-in, store billing and new realm support can require a separate native update. Use the same App Store, Google Play or TestFlight installation channel. The update links identify this app; access still depends on the current testing invitation and region. A normal web release does not trigger a store-update requirement.

Only releases explicitly marked required impose a minimum installed version/build through `/api/config.mobileAppUpdate`; publishing another store version does not automatically require it. This binary checks that policy before mounting the game and shows **Update app** and **Check again** when the installed package is too old or cannot report the required metadata. The store link is fixed per platform. Returning from the store rechecks while blocked; an active game session is not interrupted. A failed or stalled recheck retains the requirement and offers another check after the existing 15-second deadline. A higher installed version passes regardless of an older build number; the minimum build applies only at the minimum version. Publish the selected required release to the intended store/testing channels and regions before raising its minimum. See [required mobile releases](../docs/MOBILE-APP-UPDATES.md) for policy configuration, rollback and older-binary coverage. Installing this native gate still requires a new binary.

New binaries report their installed version and build from `expo-application` in that Settings page. These values come from the installed native package, not the web release or `app.json` (EAS manages build numbers remotely). Existing binaries do not acquire this reporting capability through a web deployment: they show “unavailable” and direct players to device app settings or TestFlight. Legacy binaries lacking system-browser Google/Apple sign-in also show the relevant update link on the sign-in screen. The metadata change needs a new native build and physical-device verification; changing the web code does not publish or replace any store binary.

Native releases request landscape on phones, tablets and foldables. Android declares Mossvale as a game so Android 16 large screens preserve its orientation restriction. iPad uses full screen so multitasking cannot re-enable portrait orientation. Device-owner or manufacturer overrides can still supersede app preferences.

If the realm is restarting or its sign-in settings cannot load, the app explains the server error and retries every 15 seconds while active. Startup configuration requests show a timeout and **Reconnect** after 15 seconds even if the native request or response body never settles after cancellation; late results from expired attempts are ignored. Returning to the app retries immediately; **Reconnect** also retries on demand. This recovery fix requires installing a new native app build.

The page-loading timeout allows 30 seconds without new loading progress while the app is active. Each new document load or increase in WebView progress renews that allowance; backgrounding pauses it and returning starts a fresh allowance without replacing the page. A stalled page still offers **Reconnect** and retries automatically. This recovery change requires an updated native build; a web deployment alone does not update installed apps.

Use a compatible Expo Go release or build the app. For local development, set `EXPO_PUBLIC_GAME_URL` in `.env.local` to a game server reachable from the phone (for example `http://192.168.1.10:5173/`). The Vite development server must listen on the LAN and proxy `/api/config` to the local game server. Release binaries require HTTPS; their default is `https://mossvale.world/`.

`preview` produces an installable Android APK. `simulator` produces an iOS Simulator build. `npm run build:ios` produces a signed iOS build for TestFlight/App Store; use `npm run build:ios:simulator` for the simulator. A physical iPhone ad hoc preview uses `npx eas-cli@latest build --platform ios --profile preview` after Apple signing and test-device registration. Store submission is separate from building.

The root `.easignore` limits uploads to the native app. Inspect it before adding new mobile files. The app fetches the game's public configuration to validate realm and Keycloak addresses. Other HTTPS, mail and phone links open externally.

Google, Apple, password and registration sign-in use the system authentication browser through `expo-web-browser`. The same Keycloak browser client must allow the **exact** additional redirect `mossvale://auth/callback`; its Google/Apple broker credentials stay on the server. Keycloak JS creates and retains the PKCE verifier, state and nonce in the original WebView. Native code checks the configured issuer/client, callback/state and expiry, then returns only the authorization code in a fragment to that same WebView for its existing token exchange. Account pages share this auth flow but receive no wallet/billing bridge. The Keycloak account console opens externally.

Version 1.0.2 advertises `__MOSSVALE_NATIVE_SESSION__` and remembers a successful email or wallet session using `expo-secure-store`. The existing trusted game bridge stores one encrypted record bound to the configured issuer/client, shared by the three realms; account pages cannot read it. Keycloak must refresh the saved credentials with the provider before reopening an account. Rotations and logout deletion are serialized, temporary network failures retain the encrypted session, and revoked sessions are removed. iOS uses device-only Keychain access while unlocked; Android backup rules exclude the encrypted preferences. Web storage contains only the nonsecret sign-in preference. This requires the new binary and one successful sign-in; older binaries can only reuse an existing browser SSO cookie.

The new binary advertises `__MOSSVALE_NATIVE_AUTH__`, `__MOSSVALE_NATIVE_WALLET_BROWSER__` and `__MOSSVALE_NATIVE_AUTH_LINKS__`. Deploy the corresponding web auth and wallet callback service before releasing this binary; older binaries retain their custom-scheme callback. Wallet sign-in opens the configured broker in the MetaMask, Phantom, OKX Wallet, Trust Wallet or Rabby Wallet browser. New wallet requests return to the exact Keycloak redirect `https://mossvale.world/mobile-auth/callback`. iOS Universal Links can return directly; if a wallet keeps the page open, the player switches back to Mossvale and the app retrieves the completed callback from Mossvale's own server. Native code validates the original state and issuer before resuming the WebView's existing PKCE exchange. The temporary retrieval proof stays in native memory, only travels in HTTPS POST bodies, and is discarded on completion, cancellation or expiry. No WalletConnect/Reown project, wallet SDK or per-user connection fee is required.

The EU (`mossvale.world`), US (`us.mossvale.world`) and Asia (`asia.mossvale.world`) realms serve the exact callback path and their Apple/Android association files. iOS requires the Associated Domains capability and a matching provisioning profile; retain `EXPO_NO_CAPABILITY_SYNC=1` to preserve the existing Apple sign-in capability. Android associations must use the Play app-signing certificate. Native checkout uses store billing. Adding a wallet or trusted realm requires a new native build for its chooser, app-detection entries or origin allowlists; existing binaries do not gain Asia sign-in and billing support from a web deployment.

Voucher wallet support advertises `mossvaleNative.treasureWallet`. The trusted game bridge accepts only `treasure.connect`, `treasure.sign` and `treasure.collect`; it never injects an Ethereum provider or exposes arbitrary transaction requests. A chosen wallet opens `/wallet-action.html` for a single connection, ownership signature or saved treasury claim. Creating the short-lived realm handoff uses the current account authorization only in the native HTTPS POST header; the wallet page receives only that operation. Its separate result proof stays in native memory and HTTPS POST bodies. The return link only wakes polling; results must come from the original realm using that proof. The game WebView stays mounted and signed in. Wallet choice is retained only for that game document, background requests pause, and navigation, logout or cancellation clears the pending action. Closing the wait screen cannot cancel a transaction already sent: check the payout and wallet activity before retrying. Deploy the web/server support before shipping this new native binary; older binaries show update guidance.

Phantom's direct signing deeplinks are [Solana-only](https://docs.phantom.com/phantom-deeplinks/deeplinks-ios-and-android). Its [mobile browser EVM provider](https://docs.phantom.com/ethereum-monad-testnet-base-and-polygon/getting-started) supports Robinhood Chain 4663, so voucher approvals use the existing wallet browser rather than an embedded wallet SDK. Physical-device acceptance must cover link, signature approval, claim approval/rejection, background return, and payout recovery after closing the wait screen.

OKX tries its dedicated, shared and legacy app schemes in that order. Its direct browser route retains the complete authorization URL; the current SDK confirms these schemes, while the browser path comes from its earlier documented integration. Physical Android/iOS acceptance with installed wallets remains unverified. Local URL and lifecycle checks do not prove a completed wallet signature or app return.

Rabby uses `rabbygo://go.rabby.io/mobile/?_cmd=open-dapp&dapp=<encoded authorization URL>`. The current published 0.6.87–0.6.89 code reads `dapp` through `URLSearchParams`, so encode the full URL once; older Rabby releases decoded it twice and should be updated. Its Android intent filter requires the host and `/mobile/` path, which are included when checking whether the app is installed. Android package: `com.debank.rabbymobile`; iOS query scheme: `rabbygo`. Rabby's browser injects `window.ethereum`, so the existing web sign-in provider works without a Rabby-specific web bridge. Primary references: [published version history](https://apps.apple.com/us/app/rabby-wallet-crypto-evm/id6474381673), [0.6.89 link handler](https://github.com/RabbyHub/rabby-mobile/blob/fe659c62a052e8f795eb6134f38cd0f47714ad55/apps/mobile/src/hooks/universalLink.ts), [Android intent filters](https://github.com/RabbyHub/rabby-mobile/blob/fe659c62a052e8f795eb6134f38cd0f47714ad55/apps/mobile/android/app/src/main/AndroidManifest.xml), [browser provider](https://github.com/RabbyHub/rabby-mobile/blob/fe659c62a052e8f795eb6134f38cd0f47714ad55/packages/rn-page-provider/src/index.ts).

Use a development or release build for sign-in testing; Expo Go does not own the `mossvale` callback scheme. Test email, wallet, Google and Apple on physical Android/iOS devices, including force-closing/reopening the app, offline reopen then retry, sign-out then reopen, cancelling and retrying, account-page reauthentication, switching realms, and returning after backgrounding. Local checks exercise real Keycloak refresh, secure-storage boundaries, callback validation and lifecycle cancellation; they do not prove provider credentials, device browser return or early WebView script injection work in a signed binary.

Before a future build, complete the credentials, catalog, refund/recovery, encryption-declaration review and physical-device testing described in [the purchase draft](../docs/mobile-purchases.md). Keep store listings as editable drafts; building and submission require renewed user authorization.
