# Mossvale auction settlement

For the separate MOSS burn store contract, deployment and pricing, see [Ingame store](STORE.md).

For the separate standard PONS token launch, see [Mossvale on PONS](PONS.md).

MOSS uses a separate ERC-20 settlement contract on Robinhood Chain mainnet (4663). The fixed token is [MOSS](https://robinhoodchain.blockscout.com/token/0x6742883Eef788E2424CE5a1b0d4303144AaEc0a5), with 18 decimals. The auction interface offers gold and MOSS. Existing ETH reservations retain their settlement and recovery paths.

For MOSS, deploy `MossvaleTokenAuction` from `/auction-deploy.html` with the public address of a dedicated game signing authority and the existing Mossvale treasure treasury address (`TREASURE_TREASURY_CONTRACT`). The constructor is `constructor(address gameAuthority, address treasuryRecipient)`; both addresses are permanent. Store the authority's private key only in the server secret `MOSS_AUCTION_AUTHORITY_KEY`, and set `MOSS_AUCTION_CONTRACT` to the deployed settlement address. `MOSS_AUCTION_CHAIN_ID` must be 4663. The signing authority needs no funds. The wallet deploying the contract pays ETH gas. Never send or paste signing keys into chat.

The active five-tier settlement deducts a 5% tax from each completed sale's listed price. Treasury and dev team each receive 1.25% of the purchase price; 2.5% burns before referral rewards. The buyer pays the listed price and the seller receives 95%. At 1/10/25/50/100 qualified referrals, the inviter earns 0.10%/0.25%/0.50%/0.75%/1.00% of later eligible purchase volume, deducted only from burning. For a 100 MOSS sale at the highest tier, the seller receives 95 MOSS, treasury and dev team each receive 1.25 MOSS, 1 MOSS is credited to the inviter, and 1.5 MOSS burns. Burning calls the token's burn function and reduces `totalSupply`. Tax, recipient shares and referral rewards round down to token units, with remaining fee units burned. The server reports `feeVersion: 2` only after verifying this exact runtime.

Referral rewards use the existing `proceeds(wallet)` and `withdraw(recipient)` flow. The signed order binds its original contract, referrer and rate; the contract rejects the buyer, seller and auction contract as referrer. The optional USD valuation is server-authored reservation metadata frozen at quote time and counted only after finalized settlement. Clients cannot supply it. The constructor's authority and treasury are permanent, and the fixed dev recipient needs no setting. The server verifies the exact runtime, token, authority, treasury, `TAX_BPS() == 500` and dev recipient before enabling purchases.

`src/auction-chain.mjs` pins all four production deployments. Any recognized configured address routes new reservations to the first entry, the five-tier contract. All three previous entries retain their exact runtime, original signed fee policy, settlement history and withdrawals. The previous referral contract uses `MossvaleTokenAuctionReferralLegacy.json` with the original 80/10/10 tax split and 5%/10% of the burn share at 1/50 qualified referrals; the two earlier contracts do not pay referral rewards. An outstanding order is never re-signed against a different contract. Unrecognized deployments do not inherit production routing.

When `REFERRALS_ENABLED` is absent, the program defaults on only for this recognized production route; `REFERRALS_ENABLED=0` pauses new referral activity. Activation uses the existing production settings and authority secret; it needs no environment or host Compose changes. Listings and escrowed game items are stored in the shared game database, not the settlement contract. Every existing unreserved MOSS listing carries over with its ID, seller, item, quantity and listed price intact; its next purchase uses the new contract and the 5% seller tax. No cancellation, relisting, bulk save rewrite or seller transaction is needed. Gold-only listings remain unchanged. Already-signed orders keep their original contract and terms: verify and complete any processed paid order there, or wait for a verified finalized unpaid expiry before making the same listing available for a new-contract purchase. Never re-sign an outstanding order against both contracts.

Seller balances in `proceeds(seller)` remain in the contract that earned them. The auction UI's **Collect previous MOSS** actions identify all three previous contracts and let the original seller wallet collect each balance separately; the game cannot move those funds on a seller's behalf. For an original external wallet, use Settings → Wallet → **Recover old auction proceeds**, which returns funds to that same wallet and uses its own ETH for network fees. Preserve all old addresses and their ABIs until all balances are withdrawn. Configure all realms consistently and ship normal game releases through `.github/workflows/production.yml` on `main`, including the player warning, final save and EU/US/Asia verification; do not restart realms manually for this migration.

`MOSS_AUCTION_RPC_URL` defaults to `https://robinhood-mainnet-rpc.blockreq.com/v1/rpc/public`. For this exact public endpoint, the shared chain reader obtains block headers/finality from Robinhood's official RPC and keeps historical state reads pinned to those canonical hashes on Blockreq; both providers must report chain 4663. This handles Blockreq's stale finalized tag and recent-block header limit observed on 2026-09-20 without relying on the official node's unavailable historical state. Private/custom endpoints keep their own routing and must support finalized historical state reads by canonical block hash. Use a production archive provider for long-term availability; [Robinhood's endpoint guide](https://docs.robinhood.com/chain/connecting/) lists supported providers. Reopen the auction or use **Refresh market** to reload settlement status. MOSS trading uses Mossvale Wallet and prompts for its ownership approval when a wallet link is needed.

Buyers approve only the exact purchase amount of MOSS before paying. The settlement contract verifies exact token balance changes and credits the seller, who withdraws MOSS through the auction UI. The server pins the MOSS runtime code hash and checks its token metadata and settlement authority at a finalized block. Ordinary item and Gold Exchange purchases complete after verified processed payment at a fresh canonical latest head. Their rewards can be used immediately and are not rolled back after later chain reversals; the game accepts that settlement risk. Purchases carrying frozen referral USD credit remain pending until finalized settlement, so an unfinalized purchase cannot qualify an account. Unavailable or missing configuration disables MOSS listings; it never substitutes ETH or direct transfers.

`node scripts/check-auction-token-chain.mjs` exercises ERC-20 settlement in a local EVM. `node scripts/check-auction-crypto-server.mjs --moss` checks the actual game server reservation, persistence and delivery flow using simulated chain finality. `node scripts/check-auction-crypto-server.mjs --migration` checks existing listings across a contract switch, old payment settlement, finalized expiry and restart without rewriting escrow. `node scripts/check-auction-deploy.mjs` checks setup-page constructor encoding, treasury validation, tax-split disclosure and server settings with a simulated wallet. None broadcasts a transaction.

## Legacy native ETH settlement

The contract accepts native ETH on Robinhood Chain (mainnet 4663, testnet 46630). These are the [official network settings](https://docs.robinhood.com/chain/add-network-to-wallet/). No token or contract deployment is included in the game build.

`node scripts/build-auction-contract.mjs` compiles both auction contracts to `public/contracts/`. `node scripts/check-auction-chain.mjs` deploys and exercises its bytecode in an isolated local EVM, then checks wallet ownership and finalized RPC settlement. Neither command sends a network transaction.

To enable ETH trading, store a dedicated EVM signing key in the server's `AUCTION_AUTHORITY_KEY` secret. It authorizes purchases; it does not need funds and cannot withdraw sellers' balances. Derive its public wallet address with the operator's key-management tool. Open `/auction-deploy.html`, select ETH, enter that **public** address and deploy through a funded wallet. The page defaults to mainnet, allows selecting testnet for ETH, shows the network and lets the wallet approve the deployment and gas fee. Save the displayed `AUCTION_CONTRACT`, `AUCTION_CHAIN_ID`, and `AUCTION_RPC_URL` settings with the server. Never put the signing key in a browser, repository, screenshot, log, or client environment variable. Use a dedicated production RPC provider for production traffic.

The server verifies the chain ID, finalized runtime bytecode and signing authority before it permits ETH listings. There is no fallback to direct wallet transfers or unconfirmed receipts. Failed or missing configuration disables ETH trading while gold auctions continue.

Each purchase binds a unique listing to a verified buyer wallet, seller wallet, exact amount and five-minute payment deadline. The server must persist the reserved item/order before returning the payment transaction to the buyer. The contract rejects changed orders, other buyers, expired orders and a second payment for the same listing. Sellers withdraw credited ETH through `withdraw(recipient)`; the game never holds their wallet keys.

Game items remain escrowed until `settlement(order)` returns `paid` or `expired`. Contract identity is verified at a canonical finalized block. Successful payments are checked at the fresh canonical latest head; unpaid expiry still requires a fresh finalized proof. **Do not release an item based on local time, an RPC error, a wallet cancellation, or an unverified receipt.** Robinhood is an Ethereum layer 2; finality can take longer than the five-minute payment window. A payment may finalize after that window. `paidOrders` lets the server recover a payment when the buyer closes the browser before sending a transaction hash. Paid item delivery and removing the listing must be persisted together and idempotently, including for offline buyers. Do not change the configured contract or signing key while any reservation is pending. This server settles against one deployment at a time. If configuration is changed early, restore the original contract, chain and authority to finish the reserved orders before migrating.

Wallet ownership challenges must use the authenticated character ID and server-trusted game origin. They are single-use, expire after five minutes, and authorize no payment. The current personal-sign flow supports ordinary EVM wallet accounts; contract wallets require an EIP-1271 verification path before being enabled.

## MOSS arena wagers

Equal-stake direct 1v1 wagers use the separate `MossvaleArena` escrow contract. See [ARENA.md](./ARENA.md) for the 5% pot tax, wallet deployment, recovery and staged realm activation.


### Five-tier deployment and staged activation

1. Release compatibility `904d8944de21fc7ac0be5f5f022a773370d3ed59`, which registers the new contract last while keeping the previous referral contract active. Verify this revision on EU, US and Asia before routing new purchases.
2. Verify the new deployment's finalized creation receipt, exact creation input/runtime, token, authority, treasury and dev recipient. Preserve existing reservations and their original signed addresses and terms.
3. Move the new entry first in a separate activation revision and release through `.github/workflows/production.yml`. Keep all three older entries and the existing signing key/settings.
4. Verify every realm reports the new contract, `feeVersion: 2`, a 5% tax and all three previous contracts as recovery targets, with matching assets, health, WebSockets, wiki and statistics.

Deployment alone does not activate the fee schedule. During the rolling switch, each compatible realm recovers saved orders against their original contract. Previously submitted payments stay pending until verified; old unsigned purchases can expire safely before a fresh quote. Proceeds remain at the contract that earned them and are collected separately. Once activated, any rollback must retain the four-contract compatibility revision or newer; older releases cannot recover new-contract orders.
